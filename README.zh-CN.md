## 摘要

通用 LLM Agent 做财经调研并不可靠：会编造数字，会混淆公司和财年，数据源一挂就放弃或绕圈，长任务还会撑爆上下文。本项目面向 AI 芯片行业构建调研 Agent，把这几类失败当作各自独立的工程问题，并分别评测。

Agent 起步于一个手写的工具调用循环（M1），之后重构为显式的 LangGraph 状态机。围绕这个核心，项目实现了：

- 基于 **21 份官方财报**（SEC 10-K/10-Q 与巨潮年报/半年报）的混合检索
- 能自我纠错的 **Agentic 检索**子图
- 分型长期记忆
- 增量式上下文压缩
- 可靠性层与可观测层

每个组件都要通过离线消融或故障注入测试才算验收，不靠单次演示。

| 核心结果 | 改进前 | 改进后 | 位置 |
|---|---|---|---|
| 检索 Hit@5（72 道事实题） | 0.31 | **0.93** | [§4.2](#42-检索消融) |
| 无答案题正确拒答 | 6 / 10 | **10 / 10**（误拒 0 / 75） | [§4.3](#43-agentic-检索) |
| 端到端每题工具调用次数 | 9.2 | **2.4** | [§4.4](#44-端到端) |
| 跨用户记忆隔离 | 0 / 3 | **3 / 3** | [§4.6](#46-记忆) |
| 离线回归检查（零 API 费用） | — | **287 / 287 通过** | [§4.5](#45-可靠性) |

## 1. 问题

设计由四类失败驱动，后面各节都能对应回其中一类。

| # | 失败类型 | 本项目中实际观察到的现象 | 对应方案 |
|---|---|---|---|
| P1 | **数字无出处** | 回答里的营收数字在任何来源中都找不到 | 引用、数字溯源检查、证据评估 |
| P2 | **公司或期间张冠李戴** | 问*苹果*，却用*博通*的"订阅和服务"收入作答，这段内容的 rerank 分数高达 0.91 | 元数据过滤 + 白名单、证据评估 |
| P3 | **工具不稳定** | 某轮评测里 `fetch_page` 失败率 47%，每次失败仍要走完"重试 + 退避"的全套流程 | 失败分类、熔断、运行预算 |
| P4 | **上下文耗尽** | 一段 12k 字的财报摘录就把前面的证据挤出窗口 | 增量归档、钉住区、回读工具 |

### 2.1 Agent 图

<p align="center">
  <img src="assets/figures/agent-graph.png" alt="Agent 图：主循环、工具、状态与限制三条泳道" width="100%">
</p>

<sub>**图 1.** Agent 图，分三条泳道。上：主循环负责规划、并行调用工具，并在每步之间压缩上下文。中：所有工具都运行在可靠性包装层里。下：每一步的状态都持久化到 PostgreSQL；规划前读取记忆、作答后写入记忆；超出预算的运行会被路由到 `finalize`，仍然给出答案。</sub>

每一步的图状态都会持久化到 PostgreSQL，所以一次运行可以在新进程里恢复，每一步也都能回放。手写循环版（`core/agent.py`）作为参照实现保留，**接口与图版完全一致**，整套评测无需修改就能在两者上运行。

### 2.2 Agentic 检索子图（`retrieve` 工具）

<p align="center">
  <img src="assets/figures/agentic-retrieval.drawio.png" alt="用一道真实的无答案题走一遍 Agentic 检索子图" width="100%">
</p>

<sub>**图 2.** `retrieve` 子图，用一道知识库答不了的真实问题走一遍。Query 分析发现苹果不在知识库目录里，丢弃 AAPL 过滤条件；混合检索返回一段博通的内容，分数 0.91；grade 判定公司不对，于是转去联网，汇总里把覆盖情况标为 `web_only`。</sub>

`analyze` 把问题拆成 1–3 个带元数据过滤条件的信息需求；`grade` 逐个检查公司和期间是否对得上；`pack` 去重、按证据限额截取，并把覆盖情况汇总放在最前面（详见 [§3.2](#32-agentic-检索p1p2)）。

`retrieve` 内部，每条查询走两阶段链路：

1. **召回**：**BM25**（jieba 分词，稀疏向量存在 Qdrant 中）和**向量检索**（Qwen3-Embedding）各取 30 个候选。
2. **融合与重排**：**RRF** 合并两路结果，**Qwen3-Reranker-8B** 交叉编码器重新排序，并按标定的阈值 0.5 过滤。

命中的子块最后扩展回所在的父章节。

### 2.3 技术栈

| 层 | 选型 |
|---|---|
| 编排 | LangGraph（图、`ToolNode`、Postgres checkpointer）；保留手写循环版作对照 |
| LLM | DeepSeek（OpenAI 兼容接口；可通过环境变量切换到 Kimi / OpenAI） |
| 检索 | Qdrant 1.13（稠密 + 稀疏命名向量）、Qwen3-Embedding-0.6B、Qwen3-Reranker-8B |
| 存储 | PostgreSQL 16：原文、幂等入库哈希、程序记忆、检查点 |
| 工具 | Yahoo chart 行情、DuckDuckGo 搜索、带护栏的网页抓取；同时以 **MCP 服务**（FastMCP）对外提供 |
| 可观测 | LangGraph callbacks → JSONL 日志与指标；OpenTelemetry → Phoenix |

## 3. 方法

### 3.1 语料与入库（P1、P2）

- **来源**
  - SEC 财报 15 份：英伟达、AMD、博通、英特尔、美光，各取最近两份 10-K 和一份 10-Q。
  - 巨潮报告 6 份：寒武纪、中芯国际、海光信息，各取最新年报和半年报。

  每份文档都带 `ticker`、`doc_type`、`fiscal_year`、`period_end` 和 `trust_level=official`。文件清单固定在 [`data/manifests/`](data/manifests/)，原始文件可以用 `rag/sources/fetch_*.py` 重新下载。
- **按结构解析**：SEC 的 HTML 按分页和 Item 标题切分。PDF 用 PyMuPDF 解析，表格逐行展平，因为财报数字大多在表格里。
- **父子块 + 上下文标题**：小的子块用于精确匹配，返回时给出所在的父章节作为上下文。每个块前面加上"公司 / 报告 / 章节"标题。
- **幂等入库**：内容哈希*最后*写入。中途崩溃的话，下次会重做，而不是永久跳过。哈希里含解析器版本号，修好解析器后旧文档会重新入库。

### 3.2 Agentic 检索（P1、P2）

- **Query 分析**：把问题拆成 1–3 个*信息需求*，每个需求有自己的查询和元数据过滤条件。prompt 里附带知识库目录：有哪些公司、哪些财年、各家财年截至几月。
- **过滤值白名单**：LLM 给出的每个过滤值都要对照知识库里真实存在的取值。`AAPL`、拼错的代码、未来的年份会被丢弃并记录。结果为空时，按"财年 → 文档类型 → 代码"的顺序逐级放宽。
- **证据评估**：对每个需求检查*公司和期间是否对得上*。这一步之所以必须存在，是因为光看 rerank 分数分辨不出"高度相关、但属于别家公司"的段落（§4.3）。
- **快速通道**：如果只有一个需求、过滤条件全部有效、且 top-1 ≥ 0.9，就跳过证据评估。85 道题里有 67 道走快速通道，所以评估的 LLM 成本只花在真正需要的题上。
- **覆盖情况汇总**：放在工具输出的最前面，写明 `sufficient / missing / web_only` 并附说明，告诉主 Agent 什么时候*可以停止检索*。system prompt 禁止用其他公司或其他期间的数字替代。

### 3.3 可靠性层（P3）

| 机制 | 作用 |
|---|---|
| **运行预算** | 成本、墙钟时间、LLM 调用次数、循环检测，四条独立的止损线。触发后路由到 `finalize` 节点，仍然给出答案，不会交空白 |
| **失败分类** | 分四类：瞬时、确定性、预算、副作用未知。只重试瞬时失败；遇到 403 只尝试 1 次，不再是 3 次 |
| **熔断** | 每个依赖一个三态熔断器，不再反复请求已经不可用的依赖 |
| **结构化错误** | 模型看到的是"错误原文 + 历次尝试 + 恢复建议"，不是一个裸字符串 |
| **不可信内容隔离** | 抓回来的网页包进带标记的不可信区块，并声明其中的指令不得执行。SSRF 护栏拦截私网和回环地址 |
| **持久化执行** | `PostgresSaver` 检查点，进程 A 发起的运行可以由进程 B 接着跑 |

### 3.4 记忆（P2）

- **分型**：记忆分为**情景 / 语义 / 程序**三类。
- **写入**：先由 LLM 抽取成结构化候选，代码层再强制执行硬上限。更新时先按 key 精确取代，再用向量做模糊冲突判定。
- **读取**：组合三部分：常驻画像、记忆目录、带阈值的召回。召回结果按相似度、新近度、重要性三个因子重排。
- **隔离**：`user_id` 隔离在接口层强制执行。`search_memory` 工具**没有** `user_id` 参数，而是从运行配置里读取。
- **注入方式**：召回的记忆以用户级内容注入，绝不作为 system 消息。这样来自网页的内容就不会在之后以 system 权限回到上下文里。

### 3.5 上下文压缩（P4）

- **增量归档**：不再"每圈把所有内容重新摘要一遍"，只归档越过标定高水位的轮次。
- **钉住区**：归档时抽取的事实要先用原文校验数字，通过后才*钉住*。
- **预览与回读**：长工具结果只显示预览，可以用 `read_tool_result` 按需回读。
- **失败记录**：由代码确定性地钉住，Agent 不会重复调用已经失败过的工具。
- **按工具配置预览长度**：检索结果已经筛过一遍，不该再被截断（§5 第 3 条）。

### 3.6 可观测性

挂在图配置上的 callbacks 会记录：

- 各节点耗时
- token 用量（含缓存命中部分）
- 按缓存档位计算的成本
- 工具失败与重试次数
- 结束原因

**默认不记录内容原文。** 每次运行打印一行摘要：

```
[obs] run=42216156 19.1s | LLM 4 calls (in 4694 / cached 3200, out 546) | tools 6 | plan=9.3s act=7.2s
```

同样的事件可以通过 OpenTelemetry 导出到 Phoenix，以瀑布图查看。评测报告里，质量分旁边同时给出成本和耗时。

## 4. 实验

### 4.1 实验设置

| 项 | 取值 |
|---|---|
| 语料 | 24 篇文档（21 份官方财报 + 3 篇合成的术语说明），约 9.9k 个索引块 |
| 检索 golden set | 85 道题：72 道*事实题*（中文 48 / 英文 24；数字 37 / 叙述 35）、3 道*对比题*、10 道*无答案题* |
| 相关性规则 | 包含答案原文片段的块算相关，片段已用程序校验确实逐字出现在原文里。规则只看文本，所以不同的切块方式可以用同一份题打分 |
| 端到端题集 | 14 道手写题（不来自 golden set），含一道路由反例和两道无答案题 |
| 裁判 | LLM-as-Judge 按准确性 / 完整性 / 忠实度打分，另有确定性检查：工具使用、数字溯源、引用有效性 |

<sub>**图 3.** 72 道事实题中，答案所在块没有进入前 5 的比例（1 − Hit@5），全程使用同一批 24 篇文档。按结构切块、混合检索、重排三步各自降低了失败率；两个重排模型在这里打平，区别在排序精度（Hit@1 0.72 对 0.82）。</sub>

| # | 配置 | Hit@1 | Hit@5 | Hit@30 | MRR | 时延 p50 / p95 |
|---|---|---|---|---|---|---|
| 0 | 定长 500 字切块 + 向量（v1） | 0.153 | 0.306 | 0.542 | 0.228 | 1.1 s / 1.6 s |

| 2 | 父子块 + BM25 | 0.431 | 0.653 | 0.694 | 0.516 | 44 ms / 45 ms |
| 3 | 混合（RRF） | 0.542 | 0.764 | 0.931 | 0.640 | 0.6 s / 0.9 s |
| 4 | 混合 + rerank 0.6B | 0.722 | 0.931 | 0.931 | 0.808 | 1.6 s / 2.3 s |
| **4b** | **混合 + rerank 8B** | **0.819** | **0.931** | 0.931 | **0.871** | 2.7 s / 7.2 s |

<sub>来源：[`results/retrieval/rag_offline_20261022.json`](results/retrieval/rag_offline_20261022.json)；图由 [`results/make_figures.py`](results/make_figures.py) 从该文件重新生成。</sub>

**为什么要混合检索。** 把题目分组后可以看到，两路检索失败在不同的题上：

| 题目分组 | 题数 | 向量 Hit@5 | BM25 Hit@5 | 混合 + 8B |
|---|---|---|---|---|
| 中文问英文 SEC 财报 | 21 | 0.62 | **0.05** | 0.86 |
| 问中文年报 | 24 | **0.54** | 0.88 | 0.96 |
| 英文问题 | 24 | 0.88 | 0.92 | 0.96 |

- **中文问英文财报**：问题和原文没有共同的词，BM25 几乎什么都找不到（0.05）。
- **问中文年报**：问的多是交易性金融资产、研发投入这类具体科目，正是字面匹配的强项，向量检索这里只有 0.54。

有 13 道题向量能排进前 5、BM25 却排在前 10 之外，反过来的有 6 道。

**为什么选 8B 重排模型。** 两个模型都顶到了 Hit@30 的天花板（0.931），所以区别在两点：

- **排序精度**：Hit@1 是 0.722 对 0.819。
- **有没有可用的阈值**：0.6B 下，不相关块的分数*中位数*就有 0.970，阈值设多少都分不开相关和不相关的块。8B 在阈值 0.5 处能保留 98% 的相关块，同时去掉 70% 的不相关块。

**为什么 top-k 取 5。** 第 4 / 4b 行的 Hit@3 是 0.889 / 0.917，Hit@5 和 Hit@10 都是 0.931，曲线在 5 处变平。

### 4.3 Agentic 检索

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="assets/figures/agentic-refusal-dark.png">
  <img alt="各配置在无答案题上的正确拒答数" src="assets/figures/agentic-refusal-light.png">
</picture>

<sub>**图 4.** 10 道无答案题上的正确拒答数。只做多路召回会让拒答变差；加上证据评估后恢复到 10 / 10，误拒 0 / 75。</sub>

| # | 配置 | 命中 | MRR | 正确拒答 | 误拒 | LLM token / 题 | 时延 p50 / p95 |
|---|---|---|---|---|---|---|---|
| 4b* | 混合 + 8B + 阈值，取前 5 | 0.903 | 0.850 | 6 / 10 | 0 / 75 | 0 | 2.9 s / 7.8 s |
| 5 | + query 分析 | 0.944 | 0.849 | **3 / 10** | 0 / 75 | 1,157 | 6.9 s / 28.5 s |
| 6 | + query 分析 + HyDE | 0.944 | 0.891 | 5 / 10 | 0 / 75 | 1,930 | 10.2 s / 17.1 s |
| **7** | **完整 agentic（评估 + 改写）** | **0.944** | 0.861 | **10 / 10** | **0 / 75** | 1,453 | 5.7 s / 21.8 s |

<sub>来源：[`results/retrieval/rag_agentic_20261022.json`](results/retrieval/rag_agentic_20261022.json)。</sub>

- **Query 分析找回了题**：两路检索都没捞到的 5 道题里找回了 3 道，都是"中文提问、英文措辞"的情况。中文问英文财报一组从 0.81 提升到 **1.00**。
- **只做多路召回，拒答反而变差（6 → 3 / 10）**：每多一条查询，就多一次让别家公司的段落越过阈值的机会。没有证据检查的 Agentic RAG，比普通混合检索*更危险*。
- **证据评估把拒答恢复到 10 / 10**，而且没有误伤任何可答题。
- **HyDE**：MRR 提高 0.042，代价是每题约多 770 token、多 3.3 秒。保留为开关，默认关闭。

<sub>来源：[`results/e2e/`](results/e2e/)：agentic 为 `2026-10-24_082818`，混合为 `2026-10-24_082937`，v1 为 `2026-10-22_084500`。</sub>

**怎么读这张表。**

- **通过率掩盖了差别**：v1 的知识库只有三篇术语说明，却也能过 10 / 14。原因是 Agent 会自己搜网页、抓 SEC 原文来补，每题约 6 次联网。而且多跑几轮，通过率本身就会波动 2–3 题。
- **稳定的信号是两点**：**答案从哪来**，以及 **Agent 花了多大力气**。agentic 模式下，答案几乎全部来自官方财报并带 `[ref]` 引用。覆盖情况汇总告诉 Agent 证据已经够了，所以它大约调用两次工具就停下来作答。

例子：一道无答案题（知识库里寒武纪最新的数据是 2025 年报和 2026 半年报）。

> **问：** 寒武纪 2027 年的营业收入是多少？
> **答（节选）：** 查不到这个数字。2027 年的数据还没有披露，知识库中也没有。*我不会用其他期间或其他公司的数据去替代。* 目前能查到的最新数据是：2025 年全年营业收入 649,719.62 万元（同比 +453.21%）……

### 4.5 可靠性

下面的测试全部离线且结果确定（假 LLM、录制的回放数据，只依赖本地 Qdrant），运行零 API 费用。

| 测试 | 检查项 | 锁定的行为 |
|---|---|---|
| `eval.faults` | 29 | 确定性错误不重试、瞬时错误重试；熔断开合；四条预算各自独立生效；路由到 `finalize`；不可信内容隔离 |
| `eval.compress_offline` | 82 | 切圈、增量归档、事实校验、回读、按工具配置的预览长度、降级 |
| `eval.rag_agentic_offline` | 35 | 各节点遇到坏 JSON / 超时、白名单丢弃、过滤放宽、联网兜底失败、快速通道 |
| `eval.memory_*_offline`（4 套） | 116 | 隔离、阈值、重排、取代、程序规则归纳、故障降级 |
| `eval.rag_hybrid_offline`、`eval.rag_ingest_offline` | 25 | 融合、稀疏编码、幂等入库顺序 |
| **合计** | **287 / 287 通过** | 日志：[`results/tests/`](results/tests/) |

<sub>**图 6.** 三种预算设置下，5 道回归题一轮的总成本；三种设置都是 5 / 5 通过。预算落在健康区间内会打断正常运行，反而更贵。</sub>

第一版预算凭直觉设成 ¥0.03 / 90 秒。实测健康运行的分布是 ¥0.0074–0.0533、5.8–133.6 秒，这个上限**低于最差的一次健康运行**，于是在正常工作途中就被触发了。结果是既付了已完成部分的钱，又多付一次 `finalize` 的钱，总成本多了 40%，质量毫无提升。

改法：先测出健康运行的分布，再把上限设在最差健康值的约 2 倍。标定数据记在 `core/budget.py` 里。

### 4.6 记忆

三档消融：`off` / `legacy` / `v2`。共 31 道题，每题跑 3 次，另外还专门准备了一个"弄脏"的库，里面混有旧版本记录和其他用户的数据。

| 分组 | 旧版 | **v2** |
|---|---|---|
| 基础回忆（5） | 5 / 5 | 5 / 5 |
| 链式更新（`L2_chain`） | 0 / 3 | **3 / 3** |
| 拒答（4） | 3 稳定 + 1 不稳定 | **4 / 4 稳定** |
| 跨用户隔离（3） | **0 / 3（全部泄漏）** | **3 / 3** |
| 脏库：从 6 条旧版本中取最新值 | 1 / 3 | **3 / 3** |

<sub>来源：[`results/memory/`](results/memory/)。</sub>

评测还抓出了一个设计缺陷。"我已清仓 NVDA"这道题，v2 首跑 0 / 3，旧版却是 3 / 3。原因是撤销操作把持仓记录作废后什么都没留下，问"我还持有 NVDA 吗"时，分不清是*从没持有*还是*已经清仓*。清仓是一个当前事实，不是遗忘。现在撤销持仓会用一条清仓记录取代原记录。

### 4.7 上下文压缩

在录制的回放任务上，增量归档的效果是：

- 压缩耗时占比从 41% 降到 27%
- 事实保留率从 0.58 提升到 0.73

**但它不是免费的**：输入 token 多了约 45%，成本高了约 40%。原本假设它能提高 prompt 缓存命中，这一点**没有得到证实**，因为任何一次压缩都会打断共享前缀。

按标定后的水位，真实评测题从来不会触发压缩。所以压缩的定位是兜住失控的运行，而不是日常开销。

## 5. 发现

下面这些结果改变了设计。其中大部分是*评测*本身的 bug，而不是 Agent 的 bug。

1. **落在正常区间里的护栏，只是一个随机终止器。** 预算必须根据健康运行的分布来标定（§4.5）。
2. **只考核"有没有编造"，会奖励什么都不做。** 一次 Agent 触达步数上限、交出近乎空白的答案，忠实度却拿了满分并判为通过。现在通过标准同时要求准确性和完整性，也就是考核"有没有把事办成"。
3. **裁判看到的证据至少要和 Agent 一样多。**
   - 追踪发现，上下文层把检索结果截到了 1,500 字，Agent 只看得到第一条证据。
   - 修好之后分数反而*下降*。原因是裁判自己也只看前 4,000 字，把正确且带引用的数字判成了"无依据"。
   - 两处都修完后，每题工具调用从 4.2 降到 2.4 次，回读从 0.9 降到 0 次，质量不变。
4. **数字溯源必须认得单位换算。** 原文写"$27,029 million"，回答写"270.29 亿美元"，两者对不上，答对的题被判失败。现在在原有的字面检查之外另加了一个单位感知检查，两个口径都报告，因为更宽松的口径也可能放过一个碰巧对上的编造数字。同一次复查还抓到一个真实的 10 倍错误，它藏在表格单元格里，而那正是引用校验的盲区。
5. **召回越多，召回到错误实体的也越多。** Query 拆解提高了命中，却让正确拒答减半，直到加上证据评估才恢复（§4.3）。
6. **作废不等于遗忘。** "我卖了"是一条要存下来的事实，而不是要删掉的记录（§4.6）。
7. **没起作用的机制也如实报告。** Query 改写在 85 道 golden 题上一道都没救回来，因为第一轮召回已经足够强。它仍然保留，留给更模糊的真实用户问题，而这批题测不出它的效果。

---

## 6. 局限

- **评测集偏小**：检索题 85 道、无答案题 10 道、端到端题 14 道。1–2 道题的差别属于噪声，端到端通过率在两轮之间就波动了 2–3 道。
- **golden 题是合成的**：由 LLM 看着原文出题，措辞容易贴近原文，因而偏向字面匹配。在英文问题上，BM25 甚至略高于向量检索。golden set 的人工抽检尚未完成。
- **时延**：Agentic 检索每次调用 p50 5.7 秒、p95 21.8 秒，而且评测时 embedding 有缓存。
- **覆盖面**：只有 5 家美国、3 家中国芯片公司，且只有财报。没有业绩会实录、没有新闻语料，也没有实时基本面数据。
- **无答案题的类型**：覆盖了"公司不在库里"和"期间尚未披露"，还没覆盖"指标未披露"。

## 7. 路线图

- **数据**：加入业绩会实录、扩充公司，定时抓取新财报并检测变更。
- **产品**：多租户记忆（隔离已经在接口层强制执行）、按用户的成本上限，以及把每个数字链接到出处页面的回答视图。
- **评测**：人工核验的 golden set、真实用户问题日志，以及用离线测试在 CI 里跑回归。
